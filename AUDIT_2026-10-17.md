# Inside project audit

Date: 17 October 2026. Target: https://inside-pearl.vercel.app/designers

## Verdict

The public directory has a coherent visual identity and functioning discovery basics. The reviewed code still has blockers for a real-money launch: payment reconciliation, designer payouts, and delivery of account recovery emails. The directory also exposes QA records and gives conflicting availability signals.

This is a live public-page inspection plus a focused review of local source. The deployed revision was not compared with the local commit. Backend findings describe the reviewed local implementation, not a penetration test of production.

## Checks and scope

- Live: directory loads; searching `Ravi` produces the matching profile; an unmatched query produces the explanatory empty state; Clear restores the directory; Nimal Herath's profile opens with reviews and work.
- Visual: inspected the directory and profile at the browser's available viewport, approximately 810 pixels wide. Phone and wide desktop layouts were not independently tested.
- Source: directory/profile UI, public API queries, shared form controls, authentication storage and token delivery, payment processing, metadata/sitemap, and CI.
- TypeScript: `node node_modules/typescript/bin/tsc --noEmit --incremental false` from `apps/web` fails with TS2769 at `components/site-header.test.tsx:34` and `:37`.
- Web unit tests: direct execution with `node node_modules/vitest/vitest.mjs run` passes all 42 tests across 10 files. Passing unit tests do not resolve the independent TypeScript errors.
- Standard pnpm checks could not start because the installed global pnpm reports `unable to open database file`. Direct Node execution bypasses that tool issue.
- No production records were created, modified, or deleted. No signup, email submission, payment, database migration, or authenticated workflow was exercised.
- No Lighthouse/Core Web Vitals score, automated accessibility certification, vulnerability scan, or full-project production build was completed. Performance observations below concern architecture and presentation, not measured timings.

## High priority: before accepting real customers or money

### H1. Paid milestones depend on a browser return

Evidence: `apps/api/src/payments/payments.controller.ts:50`, `apps/api/src/payments/payments.service.ts:72`, and `apps/web/components/projects/payment-list.tsx:30`.

The browser reads the Checkout return parameters and calls the endpoint that marks a milestone paid. No Stripe webhook handler was found in the API source. Closing the tab after successful payment can leave the database showing PENDING. Checkout creation also has no payment-level idempotency key or reuse of an existing session, so repeated attempts can create multiple payable sessions for one milestone.

Action: add signature-verified webhook processing, idempotent event handling, expected amount/currency checks, atomic status changes, and a retry/reconciliation path. Make repeated checkout requests reuse a valid session or otherwise prevent duplicate collection. Verify with Stripe test mode and closing the browser before redirect.

### H2. Payment release does not pay the designer

Evidence: `apps/api/src/payments/payments.service.ts:129` and `README.md`.

`release()` changes the database status to RELEASED and sends notifications; it makes no provider transfer/payout call. The README describes escrow and receiving milestone payments. Those claims exceed this implementation.

Action: explicitly label the payment workflow as a demonstration until settlement is implemented. If actual designer payouts are required, design the provider onboarding, transfer, refund, and reconciliation workflow and verify it in a test environment.

### H3. Verification and password reset tokens have no delivery path

Evidence: `apps/api/src/auth/auth.service.ts:68`, `:204`, and `:391`.

Registration and recovery create hashed tokens. Raw tokens are returned only under an explicit development flag, which is disabled in production. The reviewed flow does not send the user a verification or reset link. Production recovery therefore has no usable token delivery path in this implementation.

Action: integrate transactional email and verify delivery, expiry, single-use behavior, and recovery from delivery failures. Keep tokens out of logs and normal API responses.

### H4. QA accounts are visible in the public directory

Live evidence: `QA Other Designer 20261013-1791832347254` and `QA Flow Designer 20261013-1791832347254` appear among nine public profiles, with no work or location.

Source: `apps/api/src/designers/designers.service.ts:25`; `packages/database/prisma/schema.prisma:122`.

The directory includes every ACTIVE designer. New users default to ACTIVE, and there is no separate public-profile publication gate in this query. QA pollution reduces trust and exposes internal test naming.

Action: isolate automated testing in a separate environment and add an explicit publication/readiness policy for public profiles. Preserve an intentional path for new designers with limited work; do not silently require professional verification for everyone. Review existing QA accounts with the owner before any removal.

## Medium priority: directory reliability and usability

### M1. Availability conflicts with the hiring action

Live evidence: Nimal Herath's profile displays NOT TAKING WORK, a bio saying fully booked, and an enabled REQUEST THIS DESIGNER link.

Source: `apps/web/app/designers/[id]/page.tsx:84` and `:99`; `apps/web/components/designers/designer-card.tsx`; `apps/api/src/requests/requests.service.ts`.

The API returns availability but cards omit it. The direct-request creation path checks designer existence/status and blocking, but not availability.

Action: show availability on cards and add an Available now filter. Decide whether unavailable designers reject requests or accept future enquiries. Enforce that policy on the API and use matching button wording, such as Enquire about future availability.

### M2. Search and pagination are not represented in the URL

Live reproduction: search for Ravi; results change while the address remains `/designers`.

Source: `apps/web/app/designers/page.tsx:24-49`. Initial q/location values are read from search parameters, but subsequent filters and page changes stay in component state. Verification and page parameters are not initialized from the URL.

Impact: a copied link does not preserve results; refresh resets the search; returning from a profile can lose browsing context.

Action: make q, location, verification, and page URL-driven. Test copied links, refresh, Back, and profile-return navigation.

### M3. Discovery does not expose useful comparison criteria

Live/source evidence: filters are Search, Location, and Status; Status only offers All designers and Verified only. The backend already supports a style filter (`apps/api/src/designers/designers.service.ts:40`) that the directory does not expose.

Action: rename Status to Verification; expose style and availability first. Add a result count and clear active-filter indicators. Add budget or room-type filters only once the underlying data has a clear meaning. Avoid presenting a historical portfolio budget as the designer's fee.

### M4. Dynamic results have no accessible announcement

Source: `apps/web/app/designers/page.tsx:110`; `apps/web/components/ui/feedback.tsx`.

The debounced filter replaces results with six skeletons and then a new grid or empty-state heading. There is no result-count live region or busy state. Screen-reader users may not hear that search completed or returned zero matches. ErrorNotice correctly uses role=alert.

Action: add a concise polite status such as 1 designer found, mark the result region busy during loading, and keep focus in the edited filter. Preserve previous results while fetching where practical to reduce visual movement.

### M5. Public content is fetched after hydration

Source: `apps/web/app/designers/page.tsx:1`, `:40`; `apps/web/app/designers/[id]/page.tsx:1`, `:44`; `apps/web/lib/use-api.ts`.

Designer cards and profile body depend on a client effect. The initial render contains loading placeholders and then requires a separate API request. Profile metadata is fetched on the server, but the profile body fetches again on the client.

Action: render initial public directory/profile data on the server, then use client interactions for subsequent filtering. Measure the initial load and filter interaction before and after; do not claim a specific performance score without measurement.

### M6. Profile URLs are absent from the sitemap

Source: `apps/web/app/sitemap.ts:5`.

The sitemap lists only seven static routes. Public designer profiles and portfolio details are omitted, despite being the marketplace's main discovery content. Profile metadata is already implemented, which is a useful foundation.

Action: include eligible published profiles and portfolios, use actual modification dates, and verify that NEXT_PUBLIC_SITE_URL points to the deployed public host. The local fallback is localhost; the production environment value was not inspected.

### M7. Type checking currently fails

Reproduced: TS2769 at `apps/web/components/site-header.test.tsx:34` and `:37`. The Testing Library getByRole options do not accept `exact`.

Action: remove those options or use anchored name expressions. Run web typecheck and tests. Add explicit typecheck/lint gates to CI; the inspected workflow runs test jobs but no standalone typecheck/lint gate.

### M8. Long-lived credentials are stored in localStorage

Source: `apps/web/lib/auth-storage.ts:1-19`; `apps/web/next.config.mjs`.

Both access and refresh tokens are readable by JavaScript. An XSS flaw could steal a persistent session. This is an architectural exposure, not evidence that XSS was found. The reviewed CSP also permits inline scripts, limiting that layer's protection.

Action: prefer a server-managed session or Secure, HttpOnly refresh cookie with appropriate CSRF controls. Retain server-side session revocation, which is already present. Harden CSP incrementally and validate framework compatibility.

## Visual and content improvements

- Keep the cream/green palette, serif headings, consistent card shapes, and prominent portfolio imagery. They fit an interior-design marketplace.
- At the observed viewport, the directory's first project images begin around y=535 and the designer names fall below the initial viewport. Reduce top/section spacing enough to show at least one complete card sooner.
- Header links wrap into two lines at this intermediate width, and Designers sits tightly beside the logo. Adjust navigation gaps or move the menu breakpoint above the cramped range; verify at 768, 810, and 1024 pixels.
- Make card ratings explicit, for example 4.5 from 2 reviews; the current numeric badge is ambiguous and easy to miss. Use a readable size for useful trust information.
- Consider showing portfolio work before the full review section on profiles. Buyers can then evaluate design fit sooner.
- Change the directory description to Browse interior designers or default to verified profiles; the current sentence implies verification while the default includes unverified accounts.
- Add an explanation of what Verified means. A badge without criteria gives limited decision support.
- The inspected footer and registration UI lack privacy/terms links. Add clear product policies and support information before collecting real customer information. This is a product-readiness observation, not a legal compliance determination.

## Recommended sequence

1. Resolve payment reconciliation, payout scope, and recovery-email delivery before enabling real-money use.
2. Stop public QA pollution, fix type checking, and make the availability policy consistent.
3. Make directory state shareable; expose style/availability, result counts, and accessible status updates.
4. Improve the initial viewport and intermediate-width header layout, then measure phone/desktop performance and accessibility.
5. Re-run authenticated end-to-end hiring, recovery, and Stripe test-mode journeys in an isolated test environment.

## Audit boundaries

This audit changes no application source or production data. Security and transaction findings require targeted regression testing during remediation. Public visual inspection cannot establish correctness of admin permissions, private project access, concurrency, backups, email deliverability, or real settlement.

## Subsequent remediation: 17 October 2026

The follow-up implements the agreed demo cleanup and designer-discovery work locally:

- Directory eligibility now requires verification or at least one published portfolio. This hides the observed empty QA accounts and also keeps other unverified, unpublished accounts out of the directory. Accounts are not deleted; direct profile URLs remain viewable.
- Cards show availability and explicit review counts. Unavailable profiles have no actionable request link, and the API rejects new direct requests to unavailable designers. Existing requests are unaffected.
- Search, location, style, verification, availability, and pagination are URL-driven. Apply filters submits the draft and resets pagination. Clear removes filters; URL navigation restores the form. Results expose a count, active filters, a live announcement, and a busy state.
- Public payment descriptions and milestone controls explicitly describe a demo. Stripe live keys are rejected by the provider; test-mode keys are supported. This does not implement webhooks, reconciliation, escrow, or designer settlement.
- The intermediate-width header uses the menu layout. Directory top spacing is reduced.
- Invalid Testing Library options were removed. ESLint resolves plugins from the Next config package, and CI now checks web/API types and web lint.
- Validation: all 50 web tests and all 120 API tests pass. Web/API type checks, web lint, lint for the changed API modules, and the API build pass. Browser regression coverage was added for refresh/Back behavior and availability on desktop and phone.
- Browser end-to-end tests were not run: PostgreSQL is unavailable locally. The manual local browser attempt also timed out, and a local HTTP check reported restricted socket access. No production deployment, migration, account deletion, or payment was performed.

Remaining launch work includes verification/reset email delivery, payment reconciliation and settlement, server-rendered public content, profile sitemap entries, and session-storage hardening. The original findings above record the pre-remediation audit state.
